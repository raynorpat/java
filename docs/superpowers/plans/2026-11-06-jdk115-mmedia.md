# JDK 1.1.5 mmedia reconstruction

1. Recover Sun's three legacy AudioDevice stubs and WinMM buffer lifecycle.
2. Establish a failing Java library-load test and deterministic mu-law decoder test.
3. Reconstruct Windows 8kHz mono PCM playback, 640-sample buffers, bounded queue;
   implement Linux OSS /dev/dsp with the same decoded sample stream.
4. Compare all 256 decoded samples to Sun binary constants, Java AU parsing to
   Sun, exact exports, and real device open/write/close where available.

Device absence is an explicit skip, never a claim of playback. Linux OSS is the
new backend allowed by the approved design; it does not pretend to reproduce a
Sun Unix library. Rhapsody's implementation is Objective-C NXSoundOut and belongs
to the later Rhapsody phase.

Primary IDA inventory: mmedia_g.dll exports audioOpen_stub (10001570),
audioClose_stub (10001599), audioWrite_stub (100015ba). Native code addresses:
open 10001000, report error 10001125, queue write 1000117c, WOM_DONE callback
10001371, close 100013d2, Java write validation 10001484, mu-law decode 10001500.
Open requests PCM mono 8000Hz 16-bit, starts with 640 silent mu-law bytes (127).
Buffers contain WAVEHDR + 640 short samples + freelist pointer; at most ten
are allocated. Completion queues buffers under a critical section and signals
an auto-reset event. Close resets, waits for callbacks, closes and frees buffers.
Mu-law bias table at 10002058 is 0,132,396,924,1980,4092,8316,16764.

## Implementation and differences

The shared bridge contains only the three legacy stack stubs and Java array
validation; format parsing, mixing and channel management remain Sun's classes.
Windows follows the recovered callback/freelist/event model. Linux uses real
OSS open/ioctl/write calls, requests 8kHz mono AFMT_S16_LE, decodes the same
mu-law samples and handles partial writes and EINTR. No simulated device.

Safety differences from Sun: allocation failures do not dereference null,
writes to a closed device are ignored, buffer unprepare happens before free,
and close releases the event/critical-section resources Sun leaked. Helpers'
local names and the internal audio.h interface are reconstructed. C89 only.
Rhapsody symbols show AudioDevice Objective-C/NXSoundStream methods; that backend
is not substituted for the explicitly authorized Linux implementation.

## Verification

Red: explicit System.loadLibrary("mmedia") in AudioLibrary115 fails with
UnsatisfiedLinkError on our Phase 1 VM. (Sun's AudioDevice class alone catches
load failure and prints a diagnostic, so that weaker test was not sufficient.)

Green, isolated MSVC x86 Release and Debug: 256 decoded samples match the
original Sun AudioDevice mu-law table; AudioLibrary115 loads the library and
checks AU header/payload parsing plus truncated data. Sun's original VM gives
the same `audio library passed` result.

The real-device test dynamically resolves the three DLL stubs, opens twice,
writes more than ten 640-sample chunks (forcing completed-buffer reuse), checks
length clamping and empty/negative writes, closes, and repeats the cycle.
Both our Windows library and Sun's release DLL accepted both silent streams.
This verifies actual WinMM device submission; it is not an audible-output check.
The exact three-export oracle matches our DLL and Sun's release DLL.

Linux GCC -m32 -std=c89 -pedantic builds; decoder and Java AU consumer pass.
The device test reports `SKIP: audio device unavailable; playback unverified`
and exit 77 because this WSL host has no /dev/dsp. CTest records this as skipped,
not passed playback. Hardware verification on an OSS-equipped Linux host remains
an environment-dependent check. The backend and deterministic tests are complete.

Root integration owns the full Windows/Linux Release/Debug CTest matrix.
