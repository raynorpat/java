# JDK 1.1.5 ZIP support library

## Plan and acceptance

1. Recover the 21 Sun exports and legacy object layouts; compare original exports.
2. Run a Java consumer first against Sun and the Phase 1 VM; missing zip must fail.
3. Add only the native codec bridge and unchanged zlib 1.0.4 compression sources.
4. Compare stream, dictionary, checksums, ZIP/GZIP and archive consumers on Sun,
   Windows and Linux; verify DLL exports and jar interoperability.

## Primary evidence

`vendor/jdk1.1.5/bin/zip_g.dll`, SHA-256
99AA190D83C12A6B3A676A63AE92938BA561245A5B8D55593BB3922190D6A110,
was analyzed through IDA. The 20 exported Java functions are old stack-item
native stubs, not JNI. The remaining export is inflateFully. Both Sun zip.dll
and zip_g.dll match tools/exports-zip115.txt exactly.

Inflater fields are strm, buf, off, len, finished, needsDictionary at four-byte
intervals. Deflater shares the first four fields followed by level, strategy,
setParams, finish, finished. Java sources confirm layouts and show that ZipFile
and archive management are entirely Java. zlib provenance and original license
remain in third_party/zlib-1.0.4/ORIGIN.md and zlib.h.

## Explicit differences and historical behavior

- inflateFully uses independent state and rejects every non-END terminal error,
  preserving the existing bootstrap decoder's documented safety differences.
  The VM's bootstrap zip.c remains unchanged and still links its inflater.
- Checksum array null checks happen before dereferencing the array, avoiding
  Sun's access violation (observed with CRC32.update(null,0,0), exit C0000005).
  Array range checks use subtraction to avoid signed overflow.
- Sun Deflater.setInput(byte[]) recursively calls itself. Tests and unchanged
  archive classes use its three-argument overload; no class-library edit.
- Sun ZipInputStream checks CRC for DEFLATED, but not STORED entries. The test
  records STORED corruption being returned unchanged; GZIP/zlib checksum errors
  are rejected. No stronger Java behavior is silently substituted.
- Sun jar 1.1.5 supports c/t/x, not u. The archive test requires u to fail with
  exit 1 and `Illegal option: u`. Adding update would change shipped behavior.

## Verification

Red: our Phase 1 VM returned `UnsatisfiedLinkError: no zip in shared library path`
for ZipLibrary115, while the initial Sun consumer passed.

Green: expanded ZipLibrary115 passes Sun, isolated MSVC x86 Release DLL with our
VM, and GCC -m32 -std=c89 -pedantic DLL with our Linux VM. It checks CRC/Adler,
three-byte output streaming, raw/wrapped formats, dictionaries (wrong and right),
reset/end/counters, level/strategy changes, zero output, truncated input, bad
zlib/GZIP checksums, ZIP DEFLATED/STORED streams, ZipFile random-access reads and
truncated central directories. Sun-compiled test class is version 45.3.

Archive create/list/extract succeeds ours-to-Sun and Sun-to-ours on Windows and
ours-to-ours on Linux. The unsupported update rejection matches Sun.
Release root CTest vm-ZipLibrary115, zip-exports115 and tools-zip115-jar pass 3/3.
The export oracle matches both Sun release/debug binaries and our Release DLL.
The four added upstream files were verified byte-identical to the official
archive; existing files may use checkout-normalized line endings.

Root integration owns the complete Windows/Linux Release/Debug suite. These
isolated checks do not claim that full matrix has run yet.
