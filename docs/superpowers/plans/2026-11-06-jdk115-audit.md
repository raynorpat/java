# Phase 1 quick audit and execution ledger

## Audit

- Task 3 cannot promise a working build after replacing ABI-defining headers. Treat Tasks 3 and 4 as one integration gate, with smaller subsystem checkpoints inside Task 4.
- Task 4 is a reconstruction milestone, not an implementation-sized task. Inventory binary evidence and boot dependencies before changing the interpreter, loader, natives and platform layer together.
- A blanket CTest WILL_FAIL accepts harness failures as success. Validate oracle files and executable prerequisites separately; track the known boot failure explicitly.
- Windows oracle bytes are not universally portable. Paths, properties, default encoding and process commands need platform-specific expectations or deliberately portable assertions.
- Define whether java_test ARGS are VM options or program arguments; classpath tests require options before the class name.
- Preserve the 1.0.2 classes archive before removing classsrc, including its install dependency. Do not delete the old javap test until its replacement runs.
- The verifier, thread/GC and JNI milestones may contain boot prerequisites for Task 4. Determine those dependencies from headers and binary evidence, rather than filling gaps with untracked stubs.

## Final integration and review

Restored the original monitor/cache headers, 128-monitor initial capacity,
16-monitor expansion, per-thread cache invalidation, tagged reclamation, and
`-nm` capacity option. Native probes verify exact capacities and held-monitor
reuse; the Java churn oracle exercises four threads, collection and nested locks.
Finalizer queues now use the original four-byte intrusive link after the object
body, with newly dead batches reversed behind pending work. Pending and active
finalizers remain GC roots even when the live-finalizer queue is empty. The
original gc.h definitions are active rather than duplicated in the collector.

Completed remaining platform-header integration, original Windows path/file
wrappers, saturating floating-point conversions and MIN_VALUE/-1 arithmetic.
The classpath empty-entry regression caught mutation of a string literal;
normalization now occurs on owned copies in file wrappers, as in the primary.
Debug JCOV reads compiler metadata, records branches/switches, and writes/merges
the original report formats. Its gate compiles the fixture with our javac before
checking Sun-captured report bytes. Restored sysAtexit callbacks run in LIFO order
after finalization and before the JNI exit hook; a native oracle verifies order.

Fresh-context review inspected JNI lifecycle/references, monitor reclamation,
finalizers/selected GC paths, JCOV, conversions and file HPI, and sampled
resources, serialization and self-hosting. It identified an unlocked traversal
of JNI environment nodes while another host thread could detach and free them.
Native invocation now accesses its own embedded local-reference table directly.
The allocation-cache probe also invokes a registered JNI method concurrently
with host attachment/detachment; Windows Release passed 20 repetitions.
This is a concurrency regression guard, not a deterministic reproduction of
the old list race. The race itself was established by code inspection.

Review rulings: retain oracle-backed JNI class lookup/array-release behavior,
initializer failure semantics and DestroyJavaVM's -1 result. Detach clears
eetop before platform cleanup, so the apparent double cleanup is not a defect.
No failing monitor publication interleaving was established. Exhaustive hostile
JCOV input validation and instruction-by-instruction fidelity were not claimed;
the documented malformed-input guards and oracle cases are the verified scope.
JIT, debugger/support libraries, AWT, network/media and Rhapsody execution remain
in later phases. They are not waived Phase 1 VM-core acceptance gates.

Both Linux configurations also compile with C extensions disabled and
`-pedantic` (GCC -m32 -std=c90, equivalent to -std=c89), with no compilation
errors. Historical long-long, function-pointer and shipped-source diagnostics
remain warnings. Logs: out/phase1-c89-build-linux115.log and
out/phase1-c89-build-linux115-debug.log.

The first aggregate gates passed Windows 82/82 and Linux 77/77 in both modes.
Repetition then exposed a VMReserve115 failure under memory pressure, including
a Windows access violation in class resolution and a Linux notifier class-load
failure. This is a remaining blocker, not an accepted flaky test. Completion
and final verification will be recorded after it is resolved.

The low-memory failure was traced to two missing original lifetime mechanisms:
the separate BinClass registry monitor, and a ClassClass handle returned directly
from file/ZIP import through the resolver. A boolean import result followed by
another registry lookup lost the only live class reference. Registry mutation
also raced paused readers. Both are now reconstructed from the primary; GC takes
the registry lock before stopping threads, and readers release it before managed
allocation. Class unloading remains enabled and its native regression still
checks both normal and -noclassgc behavior. Windows and Linux Release each passed
200 exact-output reserve runs; Sun Release and Debug each passed 50.

Follow-up review found the direct handoff also requires passing the requested
class name to the existing parser, exactly as Sun's file/ZIP loaders do. Without
that check, Hello115 stored as Wrong115.class incorrectly executed. Both import
paths now reject it, with directory and compressed-ZIP cases retained in
class-name115. The harness honors JDK115_DIR and has bounded execution time.
The reviewer found no established registry lock-order/unlock defect. Deferred
debugger/JIT raw-registry consumers and untested diagnostic-hook reentrancy were
explicitly outside that review; this does not claim exhaustive callback safety.
Evidence: 2026-11-06-jdk115-class-registry-race.md.

The required reconstruction provenance line now prefixes the changed runtime,
launcher and javah sources while preserving original copyright/source banners.
Function-level primary addresses and deviation notes remain alongside the code.
